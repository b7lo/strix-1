# خارطة تطوير خوارزميات Strix

> وثيقة تنفيذ مرتبة من الأعلى أهمية إلى الأقل، لتطوير اكتشاف الحوادث، تحليل السيناريو، الفلترة، وجودة تقدير المسؤولية.

## 1. الهدف

تهدف هذه الخطة إلى رفع:

- حساسية اكتشاف الحوادث الحقيقية دون زيادة الإنذارات الكاذبة.
- ثبات النتائج بين الهواتف المختلفة ومعدلات أخذ العينات المختلفة.
- دقة اتجاه ومنطقة الاصطدام.
- دقة فهم أحداث ما قبل الاصطدام وما بعده.
- موثوقية مطابقة تقريري طرفي الحادث.
- قابلية تفسير تقدير المسؤولية ودرجة الثقة.

هذه الخوارزميات أدوات تحليل مساندة وليست حكمًا قانونيًا نهائيًا. يجب إبقاء الحالات ضعيفة الأدلة للمراجعة البشرية.

## حالة التنفيذ — 2026-08-17

- اكتملت مراحل القياس وReplay والتوقيت والكشف (Phases 0–3).
- اكتملت معايرة إطار السيارة واحتمالات المناطق (Phase 4)، مع اعتماد المستخدم ودون tag مستقل بسبب عزل Git المتاح وقت الإغلاق.
- اكتمل فصل الثقة والسيناريو والمسؤولية المحافظة (Phase 5). القواعد غير معتمدة قانونيًا وتبقى غير قطعية دون مراجعة خارجية.
- اكتملت المطابقة والاتساق الفيزيائي وRemote Config والأداء المحدود الذاكرة (Phase 6).
- نفذت سياسة جمع البيانات ومخطط الميزات وأدوات التدريب والتقييم وshadow adapter مع fallback (Phase 7 tooling).
- قرار Phase 7 هو `NO_GO_INSUFFICIENT_REVIEWED_DATA`: لا يوجد model artifact أو test set مستقل؛ لا يفعّل ML ولا يدمج افتراضيًا حتى اجتياز بوابة البيانات والمقارنة.
- وثائق الإغلاق موجودة تحت `specs/004-algorithm-improvement/`، ويبقى tag الإصدار النهائي مشروطًا بموافقة المراجعة.

---

## 2. المبدأ المعماري

يجب فصل خط المعالجة إلى مراحل واضحة:

1. **جمع البيانات:** التسارع، الجيروسكوب، GPS، الدقة، الاتجاه والتوقيت.
2. **تقييم الجودة:** معدل العينات، الفجوات، التشبع وصلاحية المعايرة.
3. **معالجة الإشارة:** إزالة الجاذبية، إزالة القيم الشاذة، ومساران سريع وناعم.
4. **اكتشاف الحدث:** هل وقع اصطدام حقيقي؟
5. **تصنيف الحدث:** المنطقة، الاتجاه، الشدة، وعدد الاصطدامات.
6. **تحليل السيناريو:** فرملة، تغيير حارة، دوران، دفع خلفي، حكة أو انقلاب.
7. **التحقق المتقاطع:** مقارنة تقرير الطرفين والتحقق الفيزيائي.
8. **تقدير المسؤولية:** قواعد قابلة للتفسير مبنية على الأدلة المتاحة.
9. **إخراج الثقة:** درجات منفصلة لجودة البيانات والحدث والسيناريو والمسؤولية.

لا ينبغي أن يؤدي ضعف مرحلة إلى نتيجة قطعية في مرحلة لاحقة.

# المرحلة P0 — حرجة وأساسية

## P0.1 بناء نظام تسجيل وإعادة تشغيل بيانات الحساسات

### المشكلة

تعديل العتبات اعتمادًا على التجربة اليدوية لا يكفي. من دون تسجيلات قابلة لإعادة التشغيل، يصعب مقارنة إصدارين من المحرك أو معرفة هل الإصلاح خفّض الإنذارات الكاذبة أم أخفى حوادث حقيقية.

### التنفيذ

إنشاء صيغة تسجيل بإصدار واضح، مثل `SensorReplayV1`، تحفظ:

- timestamp أحادي التزايد لكل عينة.
- accelerometer الخام.
- accelerometer بعد إزالة الجاذبية.
- gyroscope الخام أو المصفّى.
- سرعة GPS واتجاه الحركة ودقة الموقع والسرعة.
- معدل العينات المحسوب والفجوات.
- حالة معايرة إطار السيارة ودرجة الثقة.
- العتبات وإصدار المحرك المستخدم.
- قرار كل مرحلة وسبب القرار.
- النتيجة الصحيحة بعد المراجعة البشرية، عند توفرها.

إنشاء مشغّل Replay يمرر التسجيل إلى نفس الدوال المستخدمة أثناء القيادة، بدل إنشاء مسار تحليل مختلف للاختبارات.

### الملفات المتوقعة

- `lib/replay/types.ts`
- `lib/replay/recorder.ts`
- `lib/replay/player.ts`
- `lib/replay/fixtures/`
- اختبارات تحت `lib/__tests__/`
- دمج التسجيل الاختياري داخل `context/SessionContext.tsx`

### الخصوصية

- جعل التسجيل التشخيصي اختياريًا.
- حذف أو تقريب الموقع عند تصدير تسجيل للاختبار.
- عدم تسجيل معرفات شخصية.
- تحديد مدة احتفاظ واضحة.

### معايير القبول

- إعادة تشغيل التسجيل نفسه تعطي النتيجة نفسها دائمًا.
- يمكن مقارنة نتائج إصدارين على مجموعة التسجيلات بأمر واحد.
- لا يؤثر تفعيل التسجيل بصورة ملحوظة في معدل العينات.
- كل تسجيل يحمل إصدار المخطط وإصدار المحرك.

## P0.2 اعتماد الزمن الحقيقي بدل عدد العينات

### المشكلة

بعض الشروط تعتمد على عدد عينات ثابت، مثل 8 أو 10 عينات. هذا يعني مددًا مختلفة حسب الهاتف:

- عند `20Hz`، عشر عينات تساوي `500ms`.
- عند `50Hz`، عشر عينات تساوي `200ms`.
- عند `100Hz`، عشر عينات تساوي `100ms`.

لذلك قد يصنف الجهاز نفسه المناورة بصورة مختلفة من هاتف إلى آخر.

### التنفيذ

1. حساب الفرق الزمني لكل عينة:

$$
\Delta t_i = \frac{t_i - t_{i-1}}{1000}
$$

2. حساب معدل العينات الفعلي بنافذة متحركة، باستخدام median أو trimmed mean لتقليل تأثير الفجوات.
3. تحويل الشروط من `sampleCount` إلى `durationMs`.
4. استخدام `dt` الفعلي في jerk والفلاتر والتكامل.
5. اكتشاف:
   - عينة مكررة.
   - timestamp غير متزايد.
   - فجوة طويلة.
   - معدل عينات منخفض أو متذبذب.
6. عند الحاجة، إعادة أخذ العينات داخليًا إلى شبكة زمنية موحدة، مثل `50Hz`، باستخدام interpolation محدود، دون اختلاق بيانات داخل الفجوات الكبيرة.

### أمثلة تحويل

- `brakingSamples >= 10` يصبح `brakingDurationMs >= 200` بعد المعايرة.
- `accelSamples >= 8` يصبح `accelerationDurationMs >= 160` بعد المعايرة.
- شرط عينتين متتاليتين يصبح حدًا زمنيًا صغيرًا أو عددًا ديناميكيًا مبنيًا على معدل العينات.

### الملفات المرتبطة

- `lib/sensorUtils.ts`
- `lib/advancedAnalysis.ts`
- `lib/kalmanFilter.ts`
- `lib/dataQuality.ts`
- `context/SessionContext.tsx`

### معايير القبول

- التسجيل نفسه عند إعادة أخذ عيناته إلى `25Hz` و`50Hz` و`100Hz` يعطي التصنيف نفسه ضمن هامش محدد.
- لا يحدث قسمة على صفر أو jerk غير منتهٍ عند timestamps متطابقة.
- انخفاض معدل العينات يخفض جودة البيانات بدل إصدار ثقة عالية.

## P0.3 تحويل كشف الاصطدام إلى آلة حالات Event State Machine

### المشكلة

تجاوز عتبة التسارع وحده غير كافٍ، حتى مع debounce. المطبات، سقوط الهاتف، إغلاق الباب أو حركة الهاتف قد تنتج قمة قوية.

### الحالات المقترحة

```text
IDLE → CANDIDATE → CONFIRMED → POST_IMPACT → COOLDOWN → IDLE
              ↘ REJECTED ───────────────────────────────↗
```

### وصف الحالات

#### `IDLE`

مراقبة baseline والطريق دون وجود حدث مرشح.

#### `CANDIDATE`

تبدأ عند ظهور قمة أو jerk غير طبيعي. تُجمع نافذة قصيرة للتحقق بدل إصدار النتيجة فورًا.

#### `CONFIRMED`

يُؤكد الحدث عند تحقق حد أدنى من الأدلة المستقلة، مثل:

- peak G واضح.
- jerk مرتفع.
- نبضة قصيرة ذات شكل اصطدام.
- peak-to-average ratio مرتفع.
- تغير جيروسكوبي متزامن.
- تغير سرعة GPS معقول إذا كانت دقته جيدة.

#### `POST_IMPACT`

تجميع ما بعد الاصطدام: دوران، اصطدام ثانوي، سكون أو استمرار حركة.

#### `COOLDOWN`

منع احتساب اهتزازات الحدث نفسه كحوادث منفصلة، مع السماح بتسجيل اصطدامات ثانوية داخل نفس الحادث.

### نموذج قرار مقترح

لا يعتمد التأكيد على مجموع عشوائي فقط، بل على بوابات:

- بوابة طاقة/قوة.
- بوابة شكل النبضة.
- بوابة جودة البيانات.
- دليل إضافي واحد على الأقل عند الحالات الحدّية.

الضربة القوية جدًا يمكن تأكيدها بسرعة، بينما القيم القريبة من العتبة تحتاج مدة وأدلة أكثر.

### رفض أحداث غير حوادث

إنشاء مصنف قواعد أولي يميز:

- مطب أو حفرة: محور رأسي قوي مع نمط ارتداد وطريق مستمر.
- سقوط الهاتف: دوران هاتف كبير دون توافق GPS أو إطار السيارة.
- إغلاق باب: السيارة ساكنة ونبضة محلية قصيرة واتجاه غير متوافق.
- فرملة قوية: تسارع طولي مستمر دون نبضة اصطدام واضحة.

### الملفات المرتبطة

- `lib/sensorUtils.ts`
- ملف جديد مقترح: `lib/impactStateMachine.ts`
- `context/SessionContext.tsx`
- `lib/advancedAnalysis.ts`

### معايير القبول

- عدم تسجيل الحدث نفسه مرتين.
- فصل الاصطدامات الثانوية عن حادث جديد.
- انخفاض الإنذارات الكاذبة على تسجيلات المطبات والسقوط وإغلاق الباب.
- عدم خفض استدعاء الحوادث الحقيقية تحت الهدف المتفق عليه.

## P0.4 فصل مسار قياس الصدمة عن مسار فهم الحركة

### المشكلة

الفلتر الناعم مفيد للاتجاه والمناورات لكنه قد يخفض قمة قصيرة. أما الإشارة الخام فقد تحفظ القمة لكنها أكثر ضوضاء.

### التصميم

استخدام مسارين من المصدر نفسه:

#### مسار الصدمة السريع

- raw ناقص تقدير الجاذبية.
- إزالة القيم الشاذة المفردة بحذر.
- أقل قدر ممكن من التنعيم.
- يستخدم في `peakG` و`jerk` وشكل النبضة ومدة impulse.

#### مسار الحركة الناعم

- فلتر Kalman أو low-pass مضبوط باستخدام `dt`.
- يستخدم في الاتجاه، الفرملة، التسارع، استقرار القيادة والمناورات.

لا يجوز استخدام قيمة واحدة لكل المهام.

### تحسين مقاومة القيم الشاذة

يمكن استخدام Median أو Hampel بنافذة قصيرة جدًا، بشرط ألا يحذف نبضة اصطدام حقيقية متعددة العينات. يجب قياس أثره على بيانات replay بدل اختياره نظريًا فقط.

### تشبع الحساس

إذا بلغت القراءة سقف الحساس عدة عينات متتالية:

- تعيين `accelerometerSaturated = true`.
- اعتبار `peakG` حدًا أدنى: `peakG >= measuredMaximum`.
- خفض ثقة تقدير الشدة، لا ثقة وجود الحدث بالضرورة.

### الملفات المرتبطة

- `lib/sensorUtils.ts`
- `lib/kalmanFilter.ts`
- `lib/dataQuality.ts`

### معايير القبول

- المسار السريع يحافظ على القمم في fixtures الاصطدام.
- المسار الناعم لا ينتج اتجاهًا متذبذبًا.
- التشبع ظاهر في التقرير ولا يُعرض القياس المشبع كرقم دقيق.

# المرحلة P1 — عالية الأهمية

## P1.1 تطوير معايرة إطار السيارة واكتشاف تحرك الهاتف

### المشكلة

الجاذبية تحدد الميلان، لكنها لا تحدد yaw وحدها. إذا كان الهاتف مائلًا أو موضوعًا بعكس اتجاه السيارة، قد ينقلب الأمام والخلف أو اليمين واليسار.

يوجد أساس جيد في `vehicleFrameEstimator.ts`، ويجب تطويره ليصبح مصدرًا مستمرًا للاتجاه والثقة.

### التنفيذ

دمج الأدلة التالية:

1. **اتجاه GPS** عند سرعة ودقة كافيتين.
2. **التسارع الطولي** خلال تسارع أو فرملة مستقيمة.
3. **الجيروسكوب** لاستبعاد فترات الانعطاف من المعايرة.
4. **المغناطيسية** فقط عند استقرارها وعدم وجود تشويش واضح.
5. **Rotation vector/quaternion** إذا وفره النظام، لفصل وضعية الهاتف عن إطار العالم.

استخدام متوسط دائري موزون للزوايا بدل المتوسط الحسابي:

$$
\theta = \operatorname{atan2}\left(\sum_i w_i\sin\theta_i,\sum_i w_i\cos\theta_i\right)
$$

### اكتشاف تحرك الهاتف

إذا حدث تغير كبير وسريع في وضع الهاتف لا تفسره حركة المركبة:

- إبطال المعايرة السابقة.
- خفض `directionConfidence` فورًا.
- بدء معايرة جديدة.
- عدم إصدار منطقة اصطدام قطعية حتى تستقر المعايرة.

### المخرجات

بدل boolean فقط:

- `yawOffsetRad`
- `directionConfidence: 0..100`
- `calibrationAgeMs`
- `calibrationSources`
- `phoneMovedRecently`

### معايير القبول

- اختبار الهاتف في اتجاهات 0° و90° و180° و270° يعطي إطار سيارة متسقًا.
- عند تحريك الهاتف أثناء الجلسة، لا يستمر المحرك في استخدام معايرة قديمة.
- لا تُعرض ثقة اتجاه عالية عندما GPS ضعيف والمعايرة غير ناضجة.

## P1.2 إخراج احتمالات منطقة الاصطدام بدل قرار واحد مبكر

### المشكلة

عند قرب المتجه من الحد الفاصل بين منطقتين، فرق ضئيل قد يحول `rear-left` إلى `side-left` ويغير السيناريو والمسؤولية.

### التنفيذ

إنتاج توزيع احتمالي داخلي، مثل:

```text
rear-left: 0.55
side-left: 0.30
rear:      0.10
other:     0.05
```

يعتمد الاحتمال على:

- زاوية متجه الصدمة في إطار السيارة.
- نسبة المحور المسيطر إلى المحور الآخر.
- ثقة المعايرة.
- استقرار المتجه عبر نافذة الصدمة.
- توافق تقرير الطرف الآخر إن وجد.

يمكن إبقاء `impactZone` الحالي للتوافق، لكنه يكون `argmax` للتوزيع، مع حفظ البدائل والثقة.

### قاعدة أمان

إذا كان الفرق بين أول احتمالين صغيرًا، تعرض النتيجة كمنطقة محتملة أو تجمعهما في اتجاه أوسع بدل ادعاء دقة غير موجودة.

### معايير القبول

- تغير صغير في الزاوية لا يسبب قفزة حادة غير مبررة في المسؤولية.
- تكون احتمالات المناطق منتهية، غير سالبة، ومجموعها يساوي 1.
- انخفاض ثقة المعايرة يوسع عدم اليقين بدل اختيار منطقة خاطئة بثقة.

## P1.3 فصل درجات الثقة

### المشكلة

قد يكون وقوع الاصطدام مؤكدًا بينما اتجاهه أو المسؤولية غير واضحين. دمج كل الأدلة في رقم واحد يجعل النتيجة مضللة.

### الدرجات المقترحة

#### `dataQualityScore`

يعتمد على:

- معدل العينات والفجوات.
- تشبع الحساس.
- دقة GPS.
- اكتمال نافذة ما قبل وما بعد الحادث.
- صلاحية معايرة إطار السيارة.

#### `eventConfidence`

احتمال أن الإشارة اصطدام حقيقي وليست مطبًا أو سقوط هاتف.

#### `directionConfidence`

مدى موثوقية منطقة واتجاه الاصطدام.

#### `scenarioConfidence`

مدى كفاية الأدلة لتحديد تغيير حارة، دوران، دفع خلفي، فرملة أو غيره.

#### `liabilityConfidence`

مدى كفاية الأدلة لإصدار اقتراح مسؤولية، وتتقيد بأضعف الأدلة الضرورية.

### مبدأ التجميع

لا يكفي المتوسط. إذا كان الاتجاه ضروريًا للسيناريو وثقته منخفضة، يجب أن تحد `directionConfidence` سقف `scenarioConfidence` و`liabilityConfidence`.

### المعايرة

درجة 80% يجب أن تكون صحيحة تقريبًا في 80% من الحالات المشابهة. تقاس باستخدام:

- Brier score.
- Expected Calibration Error (ECE).
- Reliability diagrams.

### الملفات المرتبطة

- `lib/dataQuality.ts`
- `lib/liabilityEngine.ts`
- `lib/types.ts`
- `lib/reportView.ts`
- `lib/otherPartyAnalysis.ts`

### معايير القبول

- لا تكون المسؤولية قطعية إذا كانت جودة البيانات أو ثقة السيناريو منخفضة.
- يعرض التقرير سبب خفض كل درجة.
- لا تؤدي زيادة دليل إيجابي واضح إلى خفض الثقة مع ثبات بقية المدخلات، إلا عند ظهور تناقض موثق.

## P1.4 إعادة تصميم قواعد المسؤولية حول الأدلة المرورية

### المشكلة

السرعة الأعلى لا تعني تلقائيًا مسؤولية أعلى. في `lib/liability/src/crossVerification.ts` يوجد تعديل مبني على نسبة سرعتي الطرفين:

$$
\text{speedAdjust}=\left(\frac{v_A}{v_A+v_B}-0.5\right)\times30
$$

هذا قد يكون مؤشرًا للشدة أو المخالفة، لكنه ليس وحده دليلًا على من قطع مسار الآخر أو خالف الأولوية.

### ترتيب الأدلة المقترح

1. أولوية الطريق أو الإشارة المرورية إذا كانت معلومة.
2. نوع المناورة: رجوع، تغيير حارة، التفاف، دخول طريق أو تجاوز.
3. مناطق التماس المتبادلة واتساقها الفيزيائي.
4. اتجاه ومسار المركبتين قبل الاصطدام.
5. الفرملة أو المناورة التجنبية.
6. السرعة وحد الطريق إن توفر، كعامل منفصل.
7. شدة الصدمة، ولا تستخدم وحدها لتحديد المتسبب.

### تصميم المحرك

- فصل `scenarioInference` عن `liabilityRules`.
- كل قاعدة تحمل:
  - معرفًا ثابتًا.
  - الشروط.
  - الأدلة المؤيدة والمعارضة.
  - حدود التطبيق.
  - درجة الثقة.
  - مرجعًا قانونيًا/سياساتيًا عند اعتمادها رسميًا.
- إذا تعارضت السيناريوهات، لا تُختزل مباشرة إلى نسبة قطعية؛ تعرض البدائل أو تطلب مراجعة.
- إبقاء القيم النهائية القانونية `[0, 25, 50, 75, 100]` ممكن، لكن يجب حفظ `rawFaultPercent` وعدم عرضه كحقيقة عند الثقة المنخفضة.

### معايير القبول

- تغيير السرعة وحدها لا يقلب المتسبب في سيناريو ثابت إلا إذا تجاوزت قاعدة مخالفة سرعة موثقة.
- كل نتيجة مسؤولية يمكن تفسيرها بقواعد وأدلة محددة.
- الحالات مجهولة الاتجاه أو منخفضة الجودة غير قطعية.
- مجموع نسب الطرفين يساوي 100 دائمًا.

# المرحلة P2 — مهمة بعد استقرار الأساس

## P2.1 تحسين المطابقة بين تقريري الطرفين

### الوضع الحالي

المطابقة تعتمد أساسًا على الزمن والمسافة والزاوية، وهي بداية مناسبة لكنها قد تطابق حادثين متقاربين أو ترفض حادثًا بسبب GPS ضعيف.

### ميزات إضافية

- فرق وقت قمة الصدمة بعد تصحيح انجراف الساعة.
- توافق مناطق التماس، مثل أمام مقابل خلف.
- اتجاه سير المركبتين.
- عدد الاصطدامات الثانوية وتوقيتها النسبي.
- تشابه شكل النبضة بعد التطبيع، دون افتراض تطابق السعة.
- توافق التوقف أو الدوران بعد الحادث.
- دقة GPS لكل طرف، وليس الموقع فقط.

### التحقق الفيزيائي

استخدام قيود تمنع رفع الثقة عند وجود تناقض، مثل:

- الطرفان يبلغان عن خلف مركبتيهما دون تفسير متعدد الاصطدامات.
- فرق موقع كبير رغم دقة GPS عالية.
- اتجاهات حركة غير متوافقة مع مناطق التماس.
- فرق زمني يتجاوز النافذة بعد تصحيح الساعة.

### وسيلة ربط اختيارية

بعد الحادث يمكن للطرفين تبادل رمز قصير أو QR لرفع ثقة الربط، مع عدم اعتباره دليلًا على المسؤولية.

### الملفات المرتبطة

- `lib/liability/src/matching.ts`
- `lib/liability/src/crossVerification.ts`
- `lib/liability/src/types.ts`
- `artifacts/strix/lib/accidentSync.ts`

### معايير القبول

- قياس precision وrecall للمطابقة على مجموعة فيها حوادث متقاربة زمانيًا ومكانيًا.
- التناقض الفيزيائي يخفض الثقة أو يرفض المطابقة.
- غياب GPS لا يعوض تلقائيًا بزاوية واحدة فقط.

## P2.2 تحسين تحليل ما قبل الاصطدام وما بعده

### ما قبل الاصطدام

استخدام نوافذ زمنية واضحة، مع استبعاد جزء من الصدمة نفسها. تحليل:

- الفرملة ومدتها وتدرجها.
- التسارع المفاجئ.
- تغيير الحارة عبر yaw + تسارع جانبي + اتجاه GPS عند توفره.
- مناورة تجنبية.
- قيادة مستقرة قبل الحدث.
- دوران مستمر بدل قمة yaw واحدة.

### ما بعد الاصطدام

تحليل:

- الاستقرار أو استمرار الحركة.
- الدوران بعد الصدمة.
- الاصطدامات الثانوية.
- احتمالية الانقلاب.
- انفصال الهاتف عن قاعدة التثبيت، حتى لا يُفسر كحركة المركبة.

### ملاحظة مهمة

يجب أن تكون كل الحدود الزمنية مبنية على timestamps، لا عدد عينات ثابت.

### الملفات المرتبطة

- `lib/advancedAnalysis.ts`
- `lib/sensorUtils.ts`
- `context/SessionContext.tsx`

### معايير القبول

- نبضة الصدمة لا تدخل نافذة ما قبل الحادث.
- قمة yaw مفردة لا تكفي لتأكيد دوران أو U-turn.
- تغيير الحارة يحتاج توافقًا بين أكثر من حساس عند توفرها.

## P2.3 جعل العتبات قابلة للمعايرة والإصدار الآمن

### التنفيذ

يوجد `remoteConfig.ts`، ويجب ضبط استخدامه تشغيليًا:

- كل مجموعة عتبات تحمل `configVersion`.
- التحقق من الحدود المنطقية والعلاقات بين العتبات، وليس كون القيمة رقمًا فقط.
- توقيع الإعداد أو جلبه من مصدر موثوق.
- fallback محلي معروف.
- rollout تدريجي حسب نسبة المستخدمين.
- إمكانية الرجوع السريع إلى إصدار سابق.
- حفظ إصدار العتبات داخل كل تقرير وتسجيل replay.

### تجنب الخطر

لا يجوز تغيير عتبة منفردة دون اختبار تأثيرها على بقية البوابات. العتبات منظومة مترابطة.

### معايير القبول

- الإعداد غير الصالح لا يطبق جزئيًا.
- يمكن معرفة العتبات التي أنتجت أي تقرير.
- كل إصدار يمر على replay suite قبل النشر.

# المرحلة P3 — تعلم آلي بعد توفر البيانات

## P3.1 متى نستخدم التعلم الآلي؟

لا يبدأ قبل وجود dataset متنوعة وموسومة. النموذج لا يصلح نقص البيانات، بل يتعلم أخطاءها وانحيازاتها.

### الاستخدام المناسب

- التمييز بين اصطدام ومطب وسقوط هاتف وإغلاق باب.
- تصنيف شكل الحدث أو السيناريو.
- إنتاج احتمالات مناطق الاصطدام.

### الاستخدام غير المناسب مبدئيًا

- إصدار حكم مسؤولية قانوني غير قابل للتفسير.
- تقدير سرعة الطرف الآخر كرقم دقيق من هاتف واحد.
- استبدال قواعد السلامة والتحقق الفيزيائي بالكامل.

### ميزات نموذج أولي

من نافذة زمنية قصيرة:

- peak G لكل محور.
- jerk quantiles.
- impulse duration/area.
- peak-to-average ratio.
- طاقة نطاقات ترددية.
- yaw/pitch/roll rates.
- تغير سرعة واتجاه GPS.
- جودة البيانات وثقة المعايرة.

ابدأ بنموذج صغير قابل للتفسير مثل gradient boosted trees قبل شبكة عميقة على الجهاز.

### ضوابط النشر

- تشغيل shadow mode أولًا دون تغيير القرار.
- مقارنة النموذج بالقواعد على replay suite.
- fallback إلى القواعد عند نقص الميزات.
- versioning للنموذج والميزات.
- مراقبة data drift حسب الجهاز ووضع الهاتف والطريق.

# 3. استراتيجية البيانات والاختبارات

## 3.1 أنواع التسجيلات المطلوبة

### حالات سلبية

- طريق ناعم وخشن.
- مطبات وحفر بسرعات مختلفة.
- فرملة وتسارع قويان.
- انعطاف ودوار وتغيير حارة.
- إغلاق الأبواب والصندوق.
- سقوط الهاتف أو تحريكه.
- ركوب الهاتف بيد المستخدم.
- اهتزاز المحرك أثناء التوقف.

### حالات إيجابية

- اصطدام أمامي وخلفي وجانبي وزوايا ركنية.
- سرعات منخفضة ومتوسطة وعالية ضمن بيئة آمنة ومصرح بها.
- اصطدام واحد ومتعدد.
- دفع خلفي ودوران وما بعد الاصطدام.
- أوضاع تثبيت وهواتف وسيارات متعددة.

يمكن استخدام منصات اختبار أو بيانات اصطناعية للاختبارات البرمجية، لكن المعايرة النهائية تحتاج بيانات ميدانية موثوقة ومراجعة مختصين.

## 3.2 تقسيم البيانات

يجب التقسيم حسب الرحلة/السيارة/الجهاز، لا حسب العينات فقط، لمنع تسرب تسجيل واحد إلى التدريب والاختبار.

- Training.
- Validation.
- Test ثابت لا يستخدم لاختيار العتبات.
- Safety regression set للحالات الحرجة.

## 3.3 المقاييس

### اكتشاف الحادث

- Recall للحوادث الحقيقية.
- Precision.
- False alarms لكل ساعة قيادة.
- زمن التأخير حتى التأكيد.

### المنطقة والسيناريو

- Confusion matrix.
- Macro F1 بسبب عدم توازن السيناريوهات.
- Top-2 zone accuracy للحالات الحدّية.

### الثقة

- Brier score.
- ECE.
- دقة كل شريحة ثقة.

### المطابقة

- Match precision أهم من رفع عدد المطابقات الخاطئة.
- Match recall.
- حالات الرفض بسبب تناقض فيزيائي.

### المسؤولية

- الاتفاق مع مراجعة خبراء على مجموعة معلّمة.
- نسبة الحالات التي أحالها النظام للمراجعة بدل ادعاء القطعية.
- اختبارات الرتابة والثوابت القانونية/الحسابية.

# 4. اختبارات إلزامية

## اختبارات وحدات

- timestamps مكررة أو غير مرتبة.
- NaN وInfinity والقيم السالبة غير المنطقية.
- معدل عينات منخفض ومتغير.
- تشبع accelerometer.
- التفاف الزوايا عند ±180°.
- reset كامل بين الجلسات.
- احتمالات المناطق مجموعها 1.
- المسؤولية للطرفين مجموعها 100.

## اختبارات خصائص Property-Based

- لا تخرج نسبًا خارج `[0, 100]`.
- النتائج حتمية لنفس المدخلات والإصدار.
- زيادة جودة دليل مستقل لا تخفض الثقة دون تناقض.
- تغيير معدل أخذ العينات لا يغير التصنيف الأساسي.
- المدخلات غير المنتهية لا تنتج مخرجات غير منتهية.

## اختبارات Replay Regression

كل إصلاح عطل يضيف تسجيلًا أو fixture دائمًا. قبل دمج أي تعديل:

1. تشغيل جميع التسجيلات.
2. مقارنة القرارات بالإصدار المرجعي.
3. مراجعة أي تغير، حتى لو بدا تحسينًا.
4. إخراج تقرير metrics حسب الجهاز والسيناريو.

## اختبارات ميدانية

- هواتف Android متعددة وiPhone عند الدعم.
- الهاتف مثبت بأربع اتجاهات.
- طريق ناعم وخشن.
- جلسات طويلة لاختبار الذاكرة والبطارية.
- فقد GPS أو الإنترنت.
- تحريك الهاتف أثناء الجلسة.
