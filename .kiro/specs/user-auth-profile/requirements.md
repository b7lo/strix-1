# Requirements Document

<!-- وثيقة المتطلبات — المصادقة وملف المستخدم (Authentication & User Profile) -->

## Introduction

هذه الميزة تضيف نظام مصادقة كامل لتطبيق Strix (Expo/React Native) يسمح للمستخدمين
بإنشاء حساب وتسجيل الدخول عبر **البريد الإلكتروني** أو **Sign in with Apple**، مع
**ملف شخصي (Profile)** يحتوي بيانات المستخدم (الاسم، تاريخ الميلاد، المدينة، البريد،
رقم الهاتف)، وإمكانية **حذف الحساب نهائياً** (شرط إلزامي من متجر Apple).

يعتمد النظام على **Supabase Auth** للمصادقة، وجدول `profiles` في قاعدة البيانات
لتخزين البيانات الإضافية، مع تطبيق سياسات **RLS** لضمان وصول كل مستخدم لبياناته فقط.

النطاق يشمل تطبيق الموبايل (strix) بشكل أساسي، مع مراعاة التوافق مع الخدمات الحالية
(api-server, admin-dashboard, landing-page).

## Decisions — القرارات المعتمدة

هذه قرارات مثبّتة تحكم بقية المتطلبات:

- **د1 — المصادقة إلزامية**: لا يمكن استخدام التطبيق دون تسجيل دخول.
- **د2 — طريقة دخول البريد**: بريد + كلمة مرور (وليس رابطاً سحرياً)، مع تأكيد البريد
  وإعادة تعيين كلمة المرور.
- **د3 — الحد الأدنى للعمر 18 سنة**: تاريخ الميلاد إلزامي ويُتحقق منه.
- **د4 — الحقول إلزامية عند التسجيل**: الاسم، تاريخ الميلاد، المدينة، رقم الهاتف
  (البريد يأتي من مزوّد الدخول).
- **د5 — ربط الحوادث بالمستخدم**: تُربط الحوادث الجديدة بمعرّف المستخدم المصادَق.
- **د6 — سلوك حذف الحساب**: حذف كامل ونهائي — يُمسح الحساب (`auth.users`) والملف
  الشخصي وكل البيانات المرتبطة بالمستخدم بما فيها سجلات الحوادث المرتبطة به (عبر
  حذف تسلسلي/cascade)، ولا يبقى أي شيء مرتبط بالمستخدم. (متوافق مع شرط Apple)

## Prerequisites — المتطلبات المسبقة

هذه تُجهَّز خارج الكود قبل/أثناء التنفيذ:

- **Apple Developer**: عضوية فعّالة، App ID مع خاصية Sign in with Apple،
  Services ID، مفتاح `.p8` + Key ID + Team ID.
- **Supabase Auth**: تفعيل مزوّد Email ومزوّد Apple، ضبط Redirect URLs ورابط
  الـ deep link، إعداد SMTP مخصّص للإنتاج.

## Glossary

- **الزائر (Anonymous/Guest)**: مستخدم يستعمل التطبيق دون تسجيل دخول (السلوك الحالي).
- **المستخدم المصادَق (Authenticated user)**: مستخدم سجّل دخول عبر Email أو Apple.
- **الملف الشخصي (Profile)**: صف في جدول `profiles` مرتبط بـ `auth.users` عبر `id`.

## Requirements

### المتطلب 1: التسجيل عبر البريد الإلكتروني

**قصة المستخدم:** كمستخدم جديد، أريد إنشاء حساب باستخدام بريدي الإلكتروني، حتى
أتمكن من الوصول لبياناتي وحفظها.

#### معايير القبول

1. WHEN يُدخل المستخدم بريداً صالحاً وكلمة مرور مطابقة لسياسة كلمات المرور وبيانات الملف الإلزامية (الاسم، تاريخ الميلاد، المدينة، رقم الهاتف) THEN يجب على النظام إنشاء حساب في Supabase Auth وإنشاء ملفه الشخصي.
2. WHEN يكتمل إنشاء الحساب THEN يجب على النظام إرسال بريد تأكيد (verification) للمستخدم.
3. WHILE البريد غير مؤكَّد، IF حاول المستخدم الدخول THEN يجب على النظام منع الدخول وإظهار رسالة توضّح الحاجة لتأكيد البريد.
4. IF كان البريد مُستخدماً مسبقاً THEN يجب على النظام إظهار رسالة خطأ واضحة دون كشف تفاصيل حساسة.
5. WHEN يُدخل المستخدم بريداً بصيغة غير صالحة أو كلمة مرور ضعيفة THEN يجب على النظام رفض العملية وإظهار سبب الرفض.
6. IF كان عمر المستخدم المحسوب من تاريخ الميلاد أقل من 18 سنة THEN يجب على النظام رفض التسجيل وإظهار رسالة توضّح شرط العمر.

### المتطلب 2: تسجيل الدخول عبر البريد الإلكتروني

**قصة المستخدم:** كمستخدم مسجّل، أريد تسجيل الدخول ببريدي وكلمة مروري، حتى أصل
لحسابي.

#### معايير القبول

1. WHEN يُدخل المستخدم بيانات دخول صحيحة لحساب مؤكَّد THEN يجب على النظام إنشاء جلسة (session) وتوجيهه للشاشة الرئيسية.
2. IF كانت بيانات الدخول خاطئة THEN يجب على النظام إظهار رسالة خطأ عامة دون تحديد أي الحقلين خاطئ.
3. WHEN يطلب المستخدم إعادة تعيين كلمة المرور THEN يجب على النظام إرسال رابط إعادة تعيين لبريده.
4. WHEN تُنشأ جلسة بنجاح THEN يجب على النظام حفظ الجلسة بشكل آمن وتجديدها تلقائياً عند انتهائها.

### المتطلب 3: تسجيل الدخول عبر Apple

**قصة المستخدم:** كمستخدم آيفون، أريد الدخول عبر Sign in with Apple، حتى أسجّل
بسرعة دون كلمة مرور.

#### معايير القبول

1. WHEN يختار المستخدم "الدخول عبر Apple" THEN يجب على النظام بدء تدفّق Apple الأصلي (native) وإكمال المصادقة مع Supabase.
2. IF أخفى المستخدم بريده عبر Apple Private Relay THEN يجب على النظام قبول الحساب واستخدام البريد المُرحَّل دون فشل.
3. WHEN يسجّل مستخدم Apple لأول مرة THEN يجب على النظام إنشاء ملف شخصي وتعبئة الاسم من بيانات Apple إن توفّرت.
4. WHEN يعود مستخدم Apple موجود مسبقاً THEN يجب على النظام تسجيل دخوله لنفس الحساب دون تكرار.
5. IF ألغى المستخدم تدفّق Apple THEN يجب على النظام العودة لشاشة الدخول دون خطأ.

### المتطلب 4: إنشاء وإدارة الملف الشخصي

**قصة المستخدم:** كمستخدم مصادَق، أريد تعبئة وتعديل ملفي الشخصي (الاسم، تاريخ
الميلاد، المدينة، البريد، رقم الهاتف)، حتى تكون بياناتي محدّثة.

#### معايير القبول

1. WHEN يُنشأ حساب جديد (Email أو Apple) THEN يجب على النظام إنشاء صف في جدول `profiles` مرتبط بمعرّف المستخدم.
2. WHEN يفتح المستخدم شاشة الملف الشخصي THEN يجب على النظام عرض بياناته الحالية.
3. WHEN يحدّث المستخدم أي حقل صالح THEN يجب على النظام حفظ التغيير وإظهار تأكيد.
4. IF أدخل المستخدم رقم هاتف أو تاريخ ميلاد بصيغة غير صالحة THEN يجب على النظام رفض الحفظ وإظهار سبب الرفض.
5. IF عدّل المستخدم تاريخ ميلاده لقيمة تجعل عمره أقل من 18 سنة THEN يجب على النظام رفض الحفظ.
6. الحقول الإلزامية (الاسم، تاريخ الميلاد، المدينة، رقم الهاتف) يجب ألا تُترك فارغة بعد التسجيل.
7. يجب على النظام السماح للمستخدم بقراءة وتعديل ملفه الشخصي فقط دون غيره (عبر RLS).

### المتطلب 5: حذف الحساب نهائياً

**قصة المستخدم:** كمستخدم، أريد حذف حسابي وبياناتي نهائياً من داخل التطبيق، حتى
أتحكم بخصوصيتي (ولاستيفاء شرط Apple).

#### معايير القبول

1. WHEN يطلب المستخدم حذف حسابه THEN يجب على النظام طلب تأكيد صريح قبل التنفيذ.
2. WHEN يؤكّد المستخدم الحذف THEN يجب على النظام حذف حساب المصادقة (`auth.users`) وملفه الشخصي وكل البيانات المرتبطة به نهائياً.
3. WHEN يُحذف الحساب THEN يجب على النظام حذف سجلات الحوادث المرتبطة بالمستخدم أيضاً (حذف تسلسلي/cascade) بحيث لا يبقى أي شيء مرتبط به.
4. WHEN يكتمل الحذف THEN يجب على النظام إنهاء الجلسة وإعادة المستخدم لشاشة الدخول.
5. يجب على النظام تنفيذ الحذف عبر عملية آمنة على الخادم (service role) لا تُكشف مفاتيحها للتطبيق.
6. IF فشل الحذف لأي سبب THEN يجب على النظام إبقاء الحساب كما هو وإظهار رسالة خطأ دون فقدان جزئي للبيانات.

### المتطلب 6: إدارة الجلسة والتنقّل

**قصة المستخدم:** كمستخدم، أريد أن يتذكّرني التطبيق بين الجلسات ويوجّهني حسب حالة
دخولي، حتى تكون التجربة سلسة.

#### معايير القبول

1. WHEN يفتح المستخدم التطبيق ولديه جلسة صالحة THEN يجب على النظام توجيهه مباشرة للشاشة الرئيسية.
2. WHEN تنتهي صلاحية الجلسة وتعذّر تجديدها THEN يجب على النظام توجيه المستخدم لشاشة الدخول.
3. WHEN يسجّل المستخدم خروجه THEN يجب على النظام مسح الجلسة المحلية وإعادته لشاشة الدخول.
4. يجب على النظام تخزين توكنات الجلسة في تخزين آمن على الجهاز (secure storage).

### المتطلب 7: التوافق مع الاستخدام الحالي بدون تسجيل

**قصة المستخدم:** كمالك للمنتج، أريد ألا تُكسر تدفّقات الحوادث الحالية (المعتمدة على
`device_id`) عند إضافة المصادقة، حتى نطرح الميزة تدريجياً.

#### معايير القبول

1. WHEN يرفع مستخدم مصادَق حادثاً THEN يجب على النظام ربط الحادث بمعرّف المستخدم (بالإضافة إلى `device_id`).
2. يجب على النظام ربط `device_id` الحالي بالمستخدم عند أول تسجيل دخول دون فقدان بيانات.
3. بما أن المصادقة إلزامية (د1)، يجب على النظام توجيه أي مستخدم غير مسجّل لشاشة الدخول قبل الوصول لأي ميزة.
4. يجب على النظام الحفاظ على سلامة بيانات الحوادث الحالية أثناء ترحيل النموذج لإضافة عمود ربط المستخدم.
